# OMMC-20261005-customer-sync-pagination

- **Title:** Split the tablet pull into a small schedule pull and a paginated, incremental customer pull
- **Objective:** Stop the tablet sync pull from timing out with ~2.5K customers (19K for `rsm_approver`). The Salescall page pulls only its schedule; the Customers page pulls customers in resumable pages, and later pulls send only changed customers.
- **Repositories:** Portal `ommc2027`; Tablet `ommc2027-tablet` (cross-repository Work, same ID in both).
- **State:** READY_FOR_TERMINAL_REVIEW
- **Implementation authorization:** Granted by explicit Human "do the phases 1-3?" after the in-chat phased plan. Local implementation and validation only.
- **Terminal authorization:** None. A "TERMINAL: GO" was given, stopped on a portal credential failure, then withdrawn: the Human will commit and push both repositories themselves.
- **Human-authorized scope:** Phase 1 (schedule pull), Phase 2 (paginated customer pull behind a Customers-page button), Phase 3 (incremental `updated_since` + scope reconciliation). Phase 4 (removing the legacy `/sync/pull`) is out of scope.
- **Accepted decisions:**
  - Legacy `GET /api/sync/pull` stays working for tablets still on the old build.
  - Page size 500; the first customer pull runs automatically when the tablet has never completed one.
- **Implementation constraints:** No commit/push. Preserve unrelated worktree changes. Tablet device runs PHP with `max_execution_time = 30`, so each Livewire request does at most one portal page.

- **Endpoints (portal, inside the existing `SyncTokenMiddleware` group):**
  - `GET /api/sync/pull/schedule`: approved itineraries, the customers on them (active or not) with their child rows, own user row only, small lookups, own customer notes. No `customer_user`, no location tables.
  - `GET /api/sync/pull/locations`: regions, region_specifics, area_clusters, provinces, municipalities, barangays. Streamed: barangays (42,010 rows locally) are written in `lazyById(2000)` chunks as plain rows of the six columns the tablet stores; as one Eloquent collection they exhausted the 128 MB memory limit. The legacy pull also builds barangays as plain rows.
  - `GET /api/sync/pull/customers?after_id&limit&updated_since&ids`: keyset page (default 500, max 1000) of the user's active scope with child rows; `next_after_id`, `total` (first page only), `server_time`, and `scope_ids` on the last page of a scan.
  - `GET /api/sync/pull` (legacy) unchanged in shape, now built from the same service.
- **Implementation decisions:**
  - Scope logic (rsm_approver / rsm+drm_approver / drm, plus own approved-itinerary customers) moved to `TabletSyncPayload::customerScope()` as subqueries; one definition for legacy and paged pulls.
  - No `$touches` on customer child models: bumping `customers.updated_at` would make `pushCustomer()` raise false `customer_conflict` errors after a rep's own brand/category push. `updated_since` instead ORs `customer_id IN (child rows updated >= since)` across customer_brands, customer_categories, customer_trade_profiles, customer_category_histories, customer_category_events. Known gap: deleting all of a customer's brands without re-adding any is not seen incrementally.
  - `updated_since` uses `>=` and is converted to the app timezone; the watermark is the portal's `server_time` from the first page of a run, so changes made during a run are re-sent next run.
  - Tablet `pull()` now calls `/pull/schedule` (Login, Salescall page, `sync:pull` all use it) and calls `/pull/locations` only when `municipalities` is empty.
  - Tablet `pullCustomersStep()` is a checkpointed state machine in `sync_states` (`customers.pull_run`, `customers.pulled_through`): locations (first run) → pages → missing ids → done. One portal round trip per Livewire request (device `max_execution_time = 30`). A failure keeps the run so the next attempt resumes at the failed page.
  - Tablets are shared by several reps, so the run checkpoint and watermark are per local user (`customers.pull_run.{userId}`, `customers.pulled_through.{userId}`), and the last page's `scope_ids` are recorded per user in a new `customer_scopes` table (user_id, customer_id; local ids). Nothing is deactivated or deleted on scope changes: other reps may need those customers, and `expenses` cascade from `customers`. In-scope customers missing or inactive locally are fetched by id (200 per request) and added to the user's scope. The `customer_scopes` migration deletes the earlier device-wide checkpoint keys so every user starts with a full pull.
  - `customer_user` is not used for pulled visibility: it is the editable access list the tablet pushes back as `access_user_ids`. The Customers page lists, for drm and rsm/drm_approver, the existing `customer_user` matches plus the user's `customer_scopes` rows; rsm_approver still sees every active customer.
  - A failed step checkpoints the run as it was before that step, so a retry repeats the whole step instead of resuming half-applied state.
  - `upsertRows()` maps and upserts one chunk at a time (municipalities and barangays use its mapper argument), so the ~42K barangays are not held as extra full copies of the decoded payload.
  - Each payload is applied in one `DB::transaction()`; the customer loop resolves local ids with two batched lookups per 500 rows instead of one SELECT per row; pending-brand/category checks are one query each instead of one per customer.
  - Pull requests use `sync.pull_timeout` (`SYNC_PULL_TIMEOUT`, default 60s); pushes keep `sync.timeout`.
  - Customers page: "Pull Customers" button with progress, auto-start when no pull has completed or one is interrupted, re-render on completion. Salescall page: auto-start only, as a fixed toast, no re-render.
